# 架构决策记录（ADR）治理

当需要制定、评审或归档架构决策记录时，读取本文件。

## 定位

ADR 记录“为什么这么做”，是稳定决策的一等公民，与记录“现在是什么”的事实源互补：

- 事实源（architecture/ 等）：当前状态，随代码演进持续更新。
- ADR（decisions/）：决策时刻的快照，一旦 Accepted 永不改写。

## 存放与命名

- 唯一存放地：`docs/decisions/`。
- 命名：`ADR-NNN-short-name.md`，编号三位递增，例如 `ADR-007-map-sdk-maplibre.md`。
- `docs/decisions/README.md` 维护全量索引：编号、标题、状态、日期，每 ADR 一行。

## 触发条件

满足任一条件时写 ADR：

- 决策不可逆或回滚成本高。
- 决策影响模块边界、接口契约、数据模型或信任边界。
- 存在真实权衡（性能 vs 成本、一致性 vs 可用性等），未来可能被质疑。
- 偏离了官方推荐或社区惯例。

不写 ADR 的反例：琐碎实现细节、可随时回退的小决定、纯命名或格式选择、已在任务 decisions.md 中足够的过程性取舍。

## 状态机

```text
Proposed → Accepted → Superseded
              └──────→ Deprecated（决策被撤销，无替代）
```

- **Proposed**：草案，等待评审。
- **Accepted**：生效决策。正文永不修改；纠错通过新 ADR 取代。
- **Superseded**：被新决策取代。不删除文件，顶部加单向链接指向取代它的 ADR；新 ADR 中也回链被取代者。
- **Deprecated**：决策作废且无替代，同样保留文件并说明原因。

## 模板

```markdown
---
status: Accepted
decided: 2026-08-16
covers: [src/map/]
---

# ADR-NNN: 决策标题

## 背景

什么问题、什么约束、为什么现在必须决定。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 方案 A | … | … |
| 方案 B | … | … |

## 决策

选择了什么，一句话讲清。

## 理由

为什么选它，关键权衡是什么。

## 后果

- 正面：…
- 负面：…
- 需要跟进：…

## 关联

- 取代/被取代：ADR-XXX（如有）
- 产生本决策的任务：docs/tasks/日期-任务名/（如有）
```

## 与其他文档的关系

- 任务收口时，`tasks/*/日期-decisions.md` 中的稳定决策提升为 ADR；过程性取舍留在任务目录。
- 事实源只写当前结论，需要解释“为什么”时链接到对应 ADR，不复述决策过程。
- ADR 的 `covers` 是**给人看的提示**，不参与自动漂移检测——ADR 一旦 Accepted 就不修改，机器报"陈旧"没有可执行的处置动作。它的用途是：覆盖代码发生重大变更时，评审这条决策是否需要 Superseded。
