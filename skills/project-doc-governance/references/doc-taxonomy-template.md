# 文档分类模板

当仓库需要初始化 `docs/` 骨架，或现有文档边界混乱需要重组时，读取本文件。

## 入口文件分工

- 根 `README.md`：给**人**读。项目定位、快速开始、目录导航。
- 根 agent 入口文件（`AGENTS.md`，或仓库既有的 `CLAUDE.md` 等）：给 **agent** 读。可执行命令、硬规则、文档导航，≤150 行。仓库若两者并存，指定其中一个为正本，另一个只放一行指针。
- `docs/README.md`：文档体系总索引。读取顺序、各层职责、维护规则。

三者不互相复述事实；同一事实只在一个文件维护，其余位置放链接。

## 推荐读取顺序

1. agent 入口文件（agent 任务）或 `README.md`（人类上手）
2. `docs/README.md`
3. 与任务相关的领域入口，例如 `docs/architecture/README.md`
4. 领域下的最小主题文件
5. 仅当事实源无答案时，进入 `docs/tasks/` 热区；仅显式追溯时进入 archive

## 默认目录树

```text
docs/
  README.md
  architecture/
    README.md
  engineering/
    README.md
  product/
    README.md
    glossary.md
  operations/
    README.md
  decisions/
    README.md
  governance/
    README.md
  tasks/
    README.md
    archive/
      README.md
```

只为已有真实内容的领域建目录；`product/`、`operations/` 可在有内容时再建。

## 职责边界

- `docs/README.md`：导航、读取顺序、维护规则、主要目录索引。避免详细架构事实、一次性任务记录、完整排查过程。
- `docs/architecture/`：系统边界、技术基线、分层结构、不变量、租户模型、信任模型、硬约束。避免重复工程命令、迁移日记、临时任务笔记。
- `docs/engineering/`：目录放置规则、已验证启动流程、依赖兼容性、构建与验证命令。避免重新定义已由 `architecture/` 维护的架构事实。
- `docs/product/`：角色、流程、权限、业务约束、模块行为；`glossary.md` 是业务术语唯一事实源。避免实现细节和基础设施决策。
- `docs/operations/`：环境、CI/CD、中间件、监控、备份、部署拓扑。避免能力尚不存在时提前写大量猜测性文档。
- `docs/decisions/`：ADR 唯一存放地。不可逆、影响模块边界或含真实权衡的决策。规则见 `adr-governance.md`。
- `docs/governance/`：文档体系维护规则、命名规范、职责边界、路线图。避免存放实时架构事实。
- `docs/tasks/`：大任务、大阶段、专项迁移、调研的过程材料；热索引 + archive 冷索引。避免把临时过程结论直接当成稳定架构事实。

## 单文档结构

每份事实源文档应让读者在前几行拿到答案，而不是读完推导过程。建议结构：

```markdown
---
status: living
scope: code            # 无对应代码路径的文档写 process，见 freshness-policy.md
covers: [路径]
last_verified: YYYY-MM-DD
---

# 标题

> 一句话：本文件管什么、什么时候该读它。覆盖范围：…（不覆盖的一并说明）

## 结论 / 当前事实
（先说结论，再给依据）

## 细节
（可跳读的分节）
```

约束：

- **必填开头块**：一句话说明"管什么、何时读、覆盖范围"。三者合计不超过三行。
- **结论先行**：读者不看细节也能拿到可用结论。
- **长度**：事实源文档超过 400 行视为信号——需要拆分或删减（doc-lint ⑨ 会以 WARN 提示）。拆分优先于堆叠。
- **不写行号**：引用代码用符号名或路径，不写 `L123`。

## 更新方式：事实源改写，过程文档追加

这是两类文档最根本的区别，也是"文档随时间变脏"的主要来源。

| | 过程文档（`docs/tasks/`） | 事实源文档（其余各层） |
|---|---|---|
| 更新方式 | **追加**，不回改历史 | **修改**，只保留与事实匹配的内容 |
| 作废内容 | 追加新节并标注"取代 D1" | **直接改写或删除**，不留旧值 |
| 生长性 | 单向增长（正常） | 应有界；只增不减 = 在积累残渣 |
| 时间语义 | 描述某时发生了什么 | 描述当前是什么 |

事实源文档**不允许**出现：`修订史`、`已更正`、`删除线保留旧值`，以及任何形式的"曾经如此"。历史由 git 承担。

（规则文本里列举这些禁用词时，一律写进反引号——检查器会忽略行内代码，这就把"定义规则"和"违反规则"区分开了。）

## 命名规则

- 活文档（事实源）：稳定语义名，`tenant-model.md`、`build-commands.md`；历史靠 git，不靠改名。
- 过程记录与决策快照：日期前缀，`2026-08-16-research.md`。
- 任务目录：`2026-08-16-task-name/`；目录内过程文件同样日期前缀。
- `README.md` 固定作为目录入口。
- 存量旧命名不强制迁移；新文件按本规则执行。

## 索引规则

- 目录内每个 md 文件必须以 **Markdown 链接**形式被本级 README 索引；纯文本提及不算索引。不允许不可达文件（doc-lint 检查项①）。
- **索引行只写定性结论，不写精确计数**。`已有 7 篇 ADR`、`963 个单测` 这类数字必然腐烂，且没有检测手段。
- **活文档不随任务归档**：被持续性机制消费的记录（周期巡检基线、覆盖清单）收口时提升到事实源层，不留 `archive/`。
- 归档任务在 `archive/` 内层必须有带警告横幅的 README 入口。

## 图表约定

- Mermaid 内联优先：图即代码，可 diff、可评审。
- 图片资源放与文档同名的 `assets/` 子目录，例如 `tenant-model.md` 配图放 `architecture/assets/tenant-model/`。

## 渐进式披露规则

- 每层 `README.md` 先回答"这里负责什么、下一步读哪里"。
- 入口文件只保留索引和摘要，不承载完整历史。
- 长主题拆成多个职责清晰的文件；无法拆分时，在顶部提供目录和"何时读取本文件"。
- 索引层级不超过 3 跳（`docs/README.md` → 领域 README → 主题文件）；再深就说明该合并或提升。（doc-lint ① 会报告跳数 > 3 的文件。）
- 任务结束时把可复用结论提升到事实源，过程材料保留在 `tasks/`。

## 初始化输出清单

- 创建或更新根 agent 入口文件，≤150 行，写入文档治理规则与读取顺序。
- 创建 `docs/README.md`，包含读取顺序和目录职责。
- 为 `architecture/`、`engineering/` 创建 README 作为事实源入口。
- 为 `product/`、`operations/`、`decisions/`、`governance/`、`tasks/` 创建短 README（有内容预期时）。
- 每个活文档补 frontmatter（`status` / `scope` / `covers` / `last_verified`，规则见 `freshness-policy.md`）。
- 把技能母版脚本（`<技能安装目录>/scripts/doc-lint.js`）复制到 `<仓库根>/scripts/` 并登记进 agent 入口文件的验证命令区，然后运行它验证全绿。副本命名、版本比对方式见 SKILL.md 验收节。

## 重组输出清单

- 现有文件按职责边界归位；同一事实指定唯一事实源，其余位置改为链接。
- 不可达文件与死链归位或修复（doc-lint ①②）。
- **事实源文档按"改写而非追加"处理**：过时陈述核对代码后**就地改写或删除**，不留旧值、不改写为"此前为 X"。
- 无法立即核实的文档标 `status: snapshot` 并注明时点；不再有价值的直接删除（见 `freshness-policy.md` 的 deprecated 一节）。
- 补齐各层 README 索引后运行 doc-lint 验证；版本落后于母版时更新副本。
