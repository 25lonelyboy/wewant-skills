# 官方文档与经验沉淀策略

当需要为仓库规则、agent 入口文件或文档治理文件编写精确政策时，读取本文件。

## 官方文档查阅规则

凡是任务可能受到版本、平台或供应商推荐影响，优先把官方文档作为决策基线。

### 必须查阅官方文档

- 首次初始化框架、运行时、服务或脚手架。
- 升级主版本。
- 切换关键技术方案或基础设施组件。
- 引入新的基础依赖、服务或平台能力。
- 解决报错、版本冲突、环境问题或行为与预期不一致。
- 用户明确要求按官方、推荐或最新方式处理。

### 可以跳过重复查阅

- 同一会话内刚查过，结论仍然适用。
- 任务只是重复低风险且已验证过的流程。
- 任务只涉及结构清理、文案编辑或其他非技术性维护。

### 解释规则

- 只记录支撑本次决策的最小结论。
- 官方方案与社区惯例冲突时，默认采用官方方案。
- 仓库既有约束要求偏离官方方案时，在变更说明或 ADR 中写明原因。

## AGENTS.md 政策

- **体积预算**：≤150 行（doc-lint 检查项⑤）。超出部分下沉 `docs/` 并在入口文件留一行索引链接。
- **只放三类内容**：可直接执行的验证命令（build/test/lint）、硬规则（禁止项与红线）、文档导航与读取顺序。
- **标准验证命令**：`node scripts/doc-lint.js .`（副本为 `.cjs` 时相应替换；治理工具的仓库副本，初始化/重组时从技能母版落仓库，见 SKILL.md 验收节）。
- **命令可执行性**：写入的命令必须能原样复制执行；禁止"以实际为准""可以都试一下"之类的模糊表述。命令引用的脚本必须真实存在——doc-lint 的 Common Mistakes 提示过这个坑。
- **安全红线**（覆盖入口文件与全部 docs/）：禁止写入密钥、token、账号密码、私有内网地址、客户敏感信息；需要引用时用占位符 `<redacted>`。
- **禁止诱导全量阅读**：不得写"请通读全部文档"类指令；读取顺序必须是按需的索引路径。
- **docs-in-same-commit**：改变已文档化行为的代码变更，必须在同一提交内更新对应文档。

可粘贴的规则块见 `templates/agents-doc-governance-block.md`。

## 经验沉淀规则

只在任务产出可复用知识时更新仓库文档。

### 判断粒度：文档级与段落级

"该不该记"有两个层次，两层都要判断：

- **文档级**：要不要新建或更新一份文档。判据见下面的清单。
- **段落级**：某一段要不要写进这份文档。判据是——**这段会被再次复用吗？是当前的稳定事实吗？还是某条决策的依据吗？** 三者都不满足就删掉。

段落级判断是"文档随时间变脏"的主要防线。最常见的失败是：结论已经结论化了，却把得出结论的过程（被放弃的方案、当时的权衡、临时约束）一并留下。那些属于 `docs/tasks/`，或者根本不该留下。

### 需要沉淀

- 建立了可复用初始化流程、命令序列、检查清单或脚手架步骤。
- 解决了兼容性、依赖冲突、环境问题或构建验证问题。
- 明确了仓库结构、模块边界、接口契约或团队约定。
- 做出了不可逆或含真实权衡的决策（写成 ADR，见 `adr-governance.md`）。
- 该结论预计后续至少还会复用一次。

### 通常不沉淀

- 一次性改动，无法复用。
- 重复执行已有流程，没有新增结论。
- 只微调既有文档表述。
- 临时绕路方案，没有稳定经验价值。
- 未落地的设计意图（只能写入 `docs/tasks/` 的计划文档，不进事实源）。
- 得出结论的推导过程本身（结论进事实源，过程留在任务目录或丢弃）。

## 断言的可核查性

**沉默不允许**：每条实质断言要么带来源，要么带标注。既无来源也无标注的裸断言视为违规——它让"核实过的内容"和"编造的内容"在文档里完全同形。

- **内部事实**（代码、配置、目录结构）：引用真实存在的路径或符号；不写行号。
- **外部事实**（官方推荐、版本支持、供应商行为、兼容性）：必须带来源与访问日期，例如 `[官方文档](URL)，访问于 2026-10-05`。核不了的不进事实源，留在 `docs/tasks/` 并标注为判断。
- **状态标注**：`【已核实】` / `【AI 判断，待验证】`——紧凑地写结论，不写推导过程。

**标注与免责散文的区别**（必须分清，否则与"只写终态"互相抵消）：

| 允许且要求 | 禁止 |
|---|---|
| `【AI 判断，待验证】` | `本讲不提供 X，因为核实不了` |
| `覆盖范围：仅 P1 阶段` | `以下为假设性框架` |
| `来源：[官方文档](URL)，访问于 2026-10-05` | `样本不足，不外推` |

左侧是状态标签，告诉读者这条断言的效力；右侧是过程叙述，靠删掉内容来回避风险。

**诚实边界**：检查器能验证"有没有来源"，验证不了"是否真的读懂了来源"。后者依赖写入时的自觉——不要把"检测器扫过了"当成内容可靠的证据。

## 写回位置

- 架构影响 → `docs/architecture/` 的事实源。
- 工程流程、命令、兼容结论 → `docs/engineering/`。
- 业务规则与术语 → `docs/product/`（术语进 `glossary.md`）。
- 运行部署经验 → `docs/operations/`。
- 稳定决策 → `docs/decisions/`（ADR）。
- 文档维护规则 → `docs/governance/`。
- 任务计划、调研、决策过程、验证、复盘 → `docs/tasks/日期-任务名/`。

写回前检查：现有主题文件能否承载？能则补充**并就地改写**（作废的旧内容删掉，不追加"本次变更"一节），同时更新 `last_verified`；不能则新建并登记进所在目录 README 索引。

## 可放入 agent 入口文件的治理规则块

完整可粘贴版本见 `templates/agents-doc-governance-block.md`。核心六条：

- 读取顺序：入口文件 → docs/README.md → 对应领域 README → 最小主题文件；按需读取，不要求通读。
- 事实源：架构在 `docs/architecture/`，工程实践在 `docs/engineering/`，决策在 `docs/decisions/`，过程材料在 `docs/tasks/`。
- 文档与代码冲突时以代码为准，并修复文档。
- 改变已文档化行为的代码变更，同一提交内更新文档。
- 文档禁止写入密钥、token、内网地址。
- 新文档必须归位到对应层并登记进该目录 README。
