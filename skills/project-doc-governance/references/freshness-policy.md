# 文档新鲜度策略

当需要判断文档是否陈旧、制定新鲜度规则或排查"文档与代码不符"问题时，读取本文件。

## 目标定义

新鲜度的目标不是"知道文档最后修改时间"，而是**判断文档内容是否仍与事实一致**。手工时间戳只回答年龄，回答不了正确性，因此不使用手工 `更新时间` 标注。

## 两层失效机制

不同种类的断言，失效方式不同，检测手段也不同：

| 断言种类 | 因何失效 | 能否机械检测 |
|---|---|---|
| **代码事实**（模块边界、请求链、构建流程） | 代码变更 | 能：`covers` 漂移检测 |
| **外部事实**（官方推荐、版本支持、供应商行为、兼容性、价格） | **世界变化**，代码一动不动它也在腐烂 | **不能**：仓库内不可见 |

`易变事实归代码`（见预防层第 2 条）只对第一类成立。第二类无法"归代码"，只能靠**来源 + 访问日期**约束，见下文「外部事实」。

## 预防层：减少可陈旧面

1. **docs-in-same-commit**：改变已文档化行为的代码变更，必须在同一提交内更新对应文档。这是 git 能作为新鲜度信号的前提。
2. **易变事实归代码**：版本号、端口、依赖列表、API 签名、阈值配置等以代码/配置为唯一事实源，文档只写机制不抄数据。
3. **能生成就不手写**：可从代码生成的文档（API 参考、目录结构、依赖表）用脚本生成，生成物永不陈旧。
4. **不写易腐的定位符**：引用代码用符号名，不写行号；行号会被任何一次无关编辑作废，且不在 `covers` 的检测范围内。

## 检测层：frontmatter + git 漂移检测

活文档在文件头声明：

```yaml
---
status: living            # living / snapshot / deprecated
scope: code               # code（默认）/ process
covers: [src/map/, src/tenant/]   # 本文档描述的代码路径；scope: process 时可省略
last_verified: 2026-08-16         # 最后一次核对内容属实的日期
---
```

字段语义：

- `status: living`：活文档，描述当前事实，受漂移检测约束。
- `status: snapshot`：时点快照（调研报告、评审记录），不再更新，不算陈旧。
- `status: deprecated`：已失效。**默认做法是删除**，见下节。
- `scope: code`（默认）：本文档的断言可由代码核对，`covers` 必填。
- `scope: process`：本文档描述业务术语、文档规则、流程约定等**没有对应代码路径**的事实（如 `product/glossary.md`、`governance/*`）。此时不要求 `covers`，也不参与漂移检测。
- `covers`：文档描述的代码路径，漂移检测的比对对象。
- `last_verified`：最后核对属实的日期。**这是 agent 的信任依据**。

两个必须区分的概念：

- `updated`（最后编辑时间）：git 自动提供，无需手工记录；改了格式也算 updated。
- `verified`（最后核对属实）：只有对照代码确认内容仍然正确后才更新。

**agent 信任 `last_verified`，不信任编辑时间。**

`last_verified` 由 agent 自己填写，本身不构成证据。它的可信度取决于写入时是否真的核对了来源——这依赖纪律，检测器无法验证。

### 漂移检测

检测工具为仓库副本 `scripts/doc-lint.js`（或 `.cjs`，见 SKILL.md 验收节）；副本版本落后于母版时随重组更新。

对每个声明了 `covers` 的活文档，比较：

```text
文档最后 git 提交时间  vs  covers 各路径的最后 git 提交时间
```

任一覆盖路径的提交晚于文档提交 → 标记"疑似陈旧"，需要核对后更新内容并刷新 `last_verified`。仓库无 git 时跳过时间戳比对，但 `covers` 路径存在性仍会检查。

## 行为层：读取与裁决规则

1. **文档是索引，代码是事实源**：文档帮 agent 找到位置与脉络；结论影响决策时，先以最小成本核对代码或配置。
2. **冲突裁决**：文档与代码不一致时采信代码，并把修复文档作为后续动作，不允许"将就用文档结论"。
3. **陈旧标记的处理**：被漂移标记的文档只作线索（例如寻找结论的当前位置），不直接引用其结论。
4. **新鲜度核对时机**：不是每次读文档都核对，而是在"结论将影响本次决策"时核对。

## 外部事实

外部事实（官方推荐、版本支持、供应商行为、兼容性）随世界变化，仓库内无法检测其失效，因此写入时就要把可核查性固定下来：

- **必须带来源与访问日期**：`[官方文档](URL)，访问于 2026-10-05`。
- **核不了的不进事实源**：没有来源的外部断言留在 `docs/tasks/` 调研笔记并标注为判断。
- **易变数值不抄**：价格、版本号、限额等以官方页面为准，文档写机制并链接来源。
- 复核时机由来源的可变性决定，不由仓库变更决定——官方大版本发布、供应商条款变更时应复核。

## 豁免范围

以下文档不需要新鲜度管理：

- **不可变记录**：`docs/tasks/` 过程文档、ADR。它们描述"当时发生了什么/决定了什么"，天生不陈旧；ADR 过时走 Superseded 状态而非修改。
- **snapshot 与 deprecated 状态的文档**：按其性质保留原貌，不参与漂移检测。
- **纯导航文件**：各级 README 索引。索引陈旧表现为死链和不可达文件，由 doc-lint 检查项①②覆盖。

## deprecated 文档

**默认删除。** git 已经保存了历史，在 `docs/` 里保留墓碣的实际代价是：索引变脏、agent 多读一个文件，而它唯一的约束（"不直接引用结论"）恰恰是读到了就难以遵守的。

仅当能指出**具体的读者或场景**需要它时保留（例如外部链接指向它、或有明确的历史追溯需求）。保留时：

- 不进任何 README 索引
- 不参与漂移检测（由 `status: deprecated` 自动豁免）
- 不被其他文档链接

ADR 的 Superseded 不适用本条：它是"某次决策发生在某天"的客观记录，属被描述对象本身的事实，本就应该保留。
